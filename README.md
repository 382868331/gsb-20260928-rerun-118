# 应用资源调节系统（虚拟服务重放）

系统按观测、决策、执行三部分组织：

- internal/metrics：滚动窗口内的到达、完成、拒绝计数，以及等待时间统计；Snapshot 按工作者类别观测。
- internal/decision：可插拔策略，按类别分别决策，每次决策都记录可读依据。
  - QueueRateStrategy（queue-rate）：依据该类别队列高水位、平滑到达速率、估计所需工作者数，并把仍在启动延迟中的在途扩容计入已规划容量。
  - TotalQueueStrategy（queue-only）：对照策略，只看该类别队列总长度，不看速率、不计在途扩容。
- internal/executor：虚拟时钟事件引擎，负责多类工作者、任务适配约束、按类有界队列、准入拒绝、启动延迟、忙碌者优雅退出和按类扩缩容冷却。
- main.go：重放三个确定性场景并对比两个策略，决策依据落盘到 out/。

## 关键规则

- 任务携带能力类别（cpu/gpu），只有同类工作者能处理：适配约束是硬约束，gpu 任务不会因为 cpu 空闲而被处理。
- 每个类别有独立的 Min/Max、有界队列、启动延迟与冷却期；扩容决策按类别做出，不能只看总队列长度。
- 工作者进入容量后必须经过启动延迟，启动期间不能处理请求；在途扩容计入已规划容量，避免重复扩容。
- 缩容先停空闲者；忙碌者标记为 draining，只完成手头在途工作，不再领取队列任务，绝不直接消失。
- 启动中仍有资源缺口时不反向缩容；扩容后需经过冷却期，并连续观察到低流量才允许缩容，避免震荡。
- 当某类别所有在役工作者都忙且该类有界队列已满时，新请求被明确拒绝并计数；不静默丢弃请求。
- 失联的忙碌工作者不会立即消失：手头任务可能已产生外部效果，先记为未知，人工确认前不自动重放。
- 未开始的队列任务仍可重新安排；替代实例即使已就绪也只保留待命，不能据此认定旧实例已停止。
- 兼容替代必须预先声明，普通准入仍遵守任务类别亲和性；接替选择同时考虑任务成本和替代实例在途启动。
- 操作者确认旧效果已产生时释放替代实例，确认未产生时由替代实例执行剩余任务；每次安排、失联、确认、接替和释放都写入审计事件。
- 失联任务的分批人工核对走工作台：一名操作者可把多个未知任务组成一轮，对每项分别记录“已发生 / 未发生 / 材料仍不足”，提交前预览将释放哪些替代容量、安排哪些接替、保留哪些等待。
- 每个未知任务带状态版本：替代实例由在途启动进入待命就绪即递增版本；两名操作者依据不同时间的状态作决定时，只接受仍适用（任务仍未知且版本一致）的项，过期项、已被早先轮次解决的项明确列入冲突，过期决定不会重新执行已确认的效果。
- 每轮决定（含预览效果与冲突）和实际接替分别记录在核对台账；接替区分 confirmed_old_result（只是确认旧结果）与 running/completed（确已重新运行），恢复后用 `executor.LoadJournal` 追溯。
- 重放结束校验（按类别）：完成数 + 拒绝数 + 未知数 = 提交数；正常场景不存在残留队列、在途工作或未确认未知任务。

## 重放场景

- burst：短任务突发，回落后紧跟二次突发，检验是否过早缩容。
- long：长任务集中占用 gpu 专用容量，检验长占用下的扩缩容与排空。
- cap：gpu 到达速率持续超过类别上限，检验容量封顶时的明确拒绝账目。
- handoff：gpu 容量耗尽、忙碌工作者失联和缩容同时发生，人工确认后执行接替，重放等待、拒绝、未知和接替决定。

## 运行

    go test ./...
    go run .                  # 三个场景 x 两个策略，打印对比与差异解释
    go run . -v               # 额外打印每条非 hold 决策
    go run . -scenario burst -seed 7 -out out

每次运行把决策依据（时间、类别、动作、容量变化、可读原因）与分类别账目
写入 out/<场景>-<策略>.json；handoff 场景额外包含失联、确认、接替和释放审计，
并把分批核对台账单独写入 out/<场景>-<策略>-review.json（轮次决定与实际接替分字段保存）。
相同流量（同种子）重放不同策略后，
程序会定位决策轨迹的第一个分叉点并解释完成/等待/拒绝差异的来源。
